BETASEC ENGINEERING
HTTP TRAFFIC DEMONSTRATION WITH WIRESHARK


1. PURPOSE
==========

This guide explains how to use Wireshark to demonstrate that HTTP does not
encrypt information while it travels between a browser and the BetaSec
Engineering application.

This guide covers the HTTP baseline. HTTPS is now available locally; see
04_HTTPS_COMPARISON_GUIDE.txt and README.md for setup and comparison.

Relevant OWASP classification:

- OWASP Top 10:2025: A04 - Cryptographic Failures
- OWASP Top 10:2021: A02 - Cryptographic Failures

The category number changed between OWASP editions, so the project report
should state which edition it uses.


2. AUTHORIZED SCOPE AND SAFETY
==============================

Capture only traffic generated by this local project:

Host: 127.0.0.1
Port: 8000
Protocol: HTTP

Use only dummy usernames, passwords, cookies, and session data. Do not capture
traffic from unrelated applications, accounts, interfaces, or people. Do not
expose the intentionally vulnerable application to a LAN or the internet.

The server is intentionally stopped when this guide was created. Start it only
when you are ready to perform the controlled capture, and stop it afterward.


3. WHAT THE HTTP LAB DEMONSTRATES
=================================

The main HTTP Lab uses Django's normal authentication system:

Login page:
http://127.0.0.1:8000/login/

Account page:
http://127.0.0.1:8000/account/

When the browser sends the login form over HTTP, the request can contain:

- The requested path.
- The HTTP method.
- The submitted username.
- The submitted password.
- A CSRF form token.
- Cookie headers.

The password is hashed before Django stores it in the database. That protects
the stored password, but it does not protect the password while the browser is
sending it to the server. The server must receive the original password so it
can compare it with the stored hash. HTTPS is therefore required to encrypt the
transport connection.


4. WHY THE LOOPBACK CAPTURE INTERFACE IS REQUIRED
==================================================

The application is bound to 127.0.0.1. Traffic from the browser to that address
stays inside the same computer and does not travel through the normal Ethernet
or Wi-Fi adapter.

On Windows, Wireshark uses Npcap to capture localhost traffic. Select the
interface named similar to:

Adapter for loopback traffic capture

Capturing on Wi-Fi or Ethernet will usually not show requests to 127.0.0.1.
Current Wireshark Windows installers include Npcap as an installation option.
If the loopback interface is absent, confirm that Npcap and loopback capture
support were installed before attempting the demonstration.

6. START THE LOCAL HTTP SERVER
==============================

From the BetaSecEngineering directory, run:

..\venv-secproject\Scripts\python.exe manage.py runserver 127.0.0.1:8000

An equivalent Python command can be used if the environment differs:

python manage.py runserver 127.0.0.1:8000

Confirm that the address begins with http:// and that the server reports it is
listening only on 127.0.0.1:8000.


7. CAPTURE THE HTTP LOGIN
=========================

1. Open Wireshark.

2. Select Adapter for loopback traffic capture.

3. Optionally enter this capture filter before starting:

   tcp port 8000

   A capture filter limits which packets are collected. This helps ensure the
   file contains only the local demonstration traffic.

4. Start the capture.

5. In a browser, open:

   http://127.0.0.1:8000/login/

6. Sign in using the dummy main-site account.

7. Open the account page if the login does not redirect there automatically.

8. Log out using the application's logout button.

9. Stop the Wireshark capture as soon as the demonstration traffic has been
   collected.


8. FILTER THE CAPTURE
=====================

Wireshark display filters hide unrelated displayed packets without deleting
them from the capture file.

Show all traffic using the Django port:

tcp.port == 8000

Show packets Wireshark recognizes as HTTP:

http

Show HTTP requests only:

http.request

Show POST requests only:

http.request.method == "POST"

Show POST requests on the Django port:

http.request.method == "POST" && tcp.port == 8000

Show requests for the normal login path:

http.request.uri contains "/login/"

If Wireshark does not automatically decode port 8000 as HTTP, right-click a
packet, select Decode As, and assign the TCP port to HTTP for this capture.


9. FIND THE EXPOSED FORM INFORMATION
====================================

1. Select the POST request to /login/.

2. Expand Hypertext Transfer Protocol in the packet details pane.

3. Expand the HTML Form URL Encoded section if Wireshark provides it.

4. Look for the form fields:

   username
   password
   csrfmiddlewaretoken

5. Inspect the Cookie header. Depending on the point in the session, it may
   contain a CSRF cookie or a Django session cookie.

6. Right-click the packet and select Follow > TCP Stream. This reconstructs the
   conversation and can show the HTTP request headers and form body as readable
   text.

Expected observation:

The dummy username and password can be read from the HTTP POST body. Cookie and
CSRF values can also be visible in the request or response headers. The values
may be URL encoded, but URL encoding is not encryption. For example, characters
such as spaces or punctuation may be represented with percent codes and can be
decoded directly.


10. WHAT EACH OBSERVATION PROVES
================================

Visible request path and method:

An observer can learn which page the user is accessing and whether information
is being submitted.

Visible username and password:

HTTP provides no transport confidentiality. A party able to observe the
connection can read form data in transit.

Visible cookie or session identifier:

HTTP does not encrypt session tokens. If a valid session cookie is captured on
an untrusted network, it may enable session hijacking until the session expires
or is invalidated. Do not attempt to replay the token in this demonstration;
showing that it is visible is sufficient evidence.

Readable server response:

HTTP response headers and page content are also unencrypted. An active network
attacker may be able to modify traffic as well as read it.

No TLS records or encrypted application data:

The connection is ordinary HTTP over TCP. There is no TLS handshake protecting
the browser-server exchange.


11. WHAT MAKES THE HTTP SITE VULNERABLE
=======================================

HTTP does not provide the three main protections supplied by HTTPS/TLS:

Confidentiality:

Data is not encrypted, so an observer with access to the network path can read
requests and responses.

Integrity:

HTTP alone does not prevent an active attacker on the network path from
modifying content in transit.

Server authentication:

HTTP does not use a certificate to prove the identity of the server to the
browser. A user may be unable to distinguish the intended server from an
impersonator on a hostile network.

In this project, SESSION_COOKIE_HTTPONLY and SameSite=Lax provide useful browser
protections, but they do not encrypt network traffic:

- HttpOnly reduces access to the cookie from client-side JavaScript.
- SameSite helps restrict some cross-site cookie use.
- The Secure flag is disabled in HTTP mode because a Secure cookie is sent only
  over HTTPS.

None of those settings makes HTTP confidential.


12. IMPORTANT LIMITATIONS OF THE DEMONSTRATION
===============================================

The capture is performed on the same computer using the loopback interface.
This does not mean any remote person can automatically capture 127.0.0.1
traffic. Capturing local loopback traffic normally requires access to the host
and packet-capture privileges.

The experiment demonstrates a property of the HTTP protocol: if the same
unencrypted traffic crosses an untrusted network where an observer has access,
its contents are readable.

Do not write that Wireshark breaks passwords or defeats Django password
hashing. Wireshark observes the password before it reaches Django. Password
hashing protects stored credentials; TLS protects credentials in transit.

Do not write that URL encoding is encryption. It only represents characters in
a transport-safe format and is easily reversed.

=============================

Screenshot 4 - account page:

- Show the HTTP transport badge.
- Show Secure cookie status as Disabled for the HTTP run.

Suggested report structure:

Objective:
Demonstrate that HTTP transmits login information without transport encryption.

Setup:
Django on 127.0.0.1:8000, dummy account, Npcap loopback capture, and a capture
filter limited to TCP port 8000.

Test:
Submit the main login form while capturing the loopback interface.

Observed result:
The POST body and dummy credentials are readable in Wireshark.

Risk:
An observer on an untrusted network path could read credentials, cookies, and
page content or potentially alter unprotected traffic.

Mitigation:
Serve the application through HTTPS using a trusted certificate, redirect HTTP
to HTTPS, and enable Secure cookies once HTTPS is active.

Lesson:
Password hashing protects stored passwords, while HTTPS is required to protect
passwords and session data during transmission.
