BETASEC ENGINEERING
SQL INJECTION: VULNERABLE AND SECURE SITE GUIDE


1. PURPOSE AND SCOPE
====================

This guide explains the two SQL-injection demonstration pages in the local
BetaSec Engineering application:

Vulnerable page:
http://127.0.0.1:8000/lab/sql-injection/vulnerable/

Secure comparison:
http://127.0.0.1:8000/lab/sql-injection/secure/

Both pages are restricted to localhost and use the separate LabAccount model.
They do not authenticate a normal Django user and must use only the supplied
dummy account:

Username: analyst
Password: secengy124!

The intentionally unsafe code exists only in accounts/views.py inside the
lab_vulnerable_login view. It must never be copied into a real application or
made accessible from a LAN or the internet.


2. WHAT SQL INJECTION IS
========================

SQL injection occurs when an application combines untrusted user input with an
SQL command as text. If the input is inserted directly into the command, the
database may interpret part of the input as SQL syntax instead of treating the
whole value as data.

The problem is not simply that the input contains an apostrophe. The problem is
that the vulnerable application places that apostrophe and the rest of the
input directly into an executable SQL string.

OWASP classification:

- OWASP Top 10:2025: A05 - Injection
- OWASP Top 10:2021: A03 - Injection
- Relevant weakness: CWE-89, Improper Neutralization of Special Elements used
  in an SQL Command (SQL Injection)

The report should identify which OWASP edition it uses because the category
number changed between 2021 and 2025.


3. HOW THE VULNERABLE PAGE WORKS
================================

The vulnerable view receives two HTTP form parameters:

- username
- password

It then builds an SQL query by inserting both values directly into a Python
formatted string. In simplified form, the query is:

SELECT id, username, display_name
FROM accounts_labaccount
WHERE username = '<username>'
AND lab_password = '<password>'
LIMIT 1

With the legitimate dummy credentials, the completed query is conceptually:

SELECT id, username, display_name
FROM accounts_labaccount
WHERE username = 'analyst'
AND lab_password = 'secengy124!'
LIMIT 1

The database finds the matching dummy record. The application then creates a
lab-only session and redirects to the result page.

Important terminology:

The values submitted by the form are HTTP form parameters. In the vulnerable
implementation they are not SQL parameters or bound parameters. They are raw
text inserted into the SQL command. The classroom attack string is better
described as an SQL-injection payload.


4. THE CLASSROOM SQL-INJECTION PAYLOAD
======================================

Enter this value in the username field:

' OR 1=1 --

Use any incorrect value in the password field, for example:

incorrect

The payload consists of these parts:

1. The apostrophe: '

   This closes the username string that the application started in the SQL
   query. The application already supplied the opening apostrophe.

2. The Boolean operator: OR

   This adds an alternative condition to the WHERE clause. Only one side of an
   OR expression needs to be true.

3. The expression: 1=1

   This is always true. It makes the WHERE clause true even when the supplied
   username and password are not valid credentials.

4. The comment marker: --

   In this SQLite demonstration, the two hyphens begin an SQL comment. The
   remaining text generated by the application, including the password check
   and unmatched quote, is ignored by the SQL parser.

After substitution, the vulnerable query is conceptually:

SELECT id, username, display_name
FROM accounts_labaccount
WHERE username = '' OR 1=1 --' AND lab_password = 'incorrect' LIMIT 1

The effective logic is therefore approximately:

WHERE username = '' OR TRUE

Because that condition is true for the dummy rows, SQLite returns a record.
The LIMIT 1 clause means only the first matching record is used. The application
mistakenly treats the returned row as proof that authentication succeeded.

Why the password no longer matters:

The password expression appears after the -- comment marker, so it is not part
of the effective SQL command. The attacker has changed the structure and
meaning of the query instead of guessing the password.


5. EXPECTED VULNERABLE-PAGE RESULTS
===================================

Test A - legitimate dummy credentials:

Username: analyst
Password: secengy124!
Expected result: successful lab session and redirect to the result page.

Test B - injection attempt:

Username: ' OR 1=1 --
Password: incorrect
Expected result: successful lab session despite the incorrect password.

This demonstrates an authentication bypass caused by SQL injection. It does
not reveal a real password, and it should not be extended to data extraction,
destructive queries, operating-system commands, or any non-local target.


6. HOW THE SECURE PAGE WORKS
============================

The secure view receives the same username and password fields, but it uses the
Django Object-Relational Mapper (ORM):

LabAccount.objects.filter(
    username=form.cleaned_data['username'],
    lab_password=form.cleaned_data['password'],
).values('id', 'username', 'display_name').first()

The ORM creates a parameterized database query. Conceptually, it separates the
SQL command from the values:

SELECT id, username, display_name
FROM accounts_labaccount
WHERE username = ? AND lab_password = ?
LIMIT 1

Bound value 1: the submitted username
Bound value 2: the submitted password

The exact placeholder syntax can vary by database driver, but the security
property is the same: the SQL structure is prepared separately from the data.


7. WHY THE SAME PAYLOAD FAILS ON THE SECURE PAGE
=================================================

When the username is:

' OR 1=1 --

the ORM treats every character as part of one username value. The apostrophe,
OR expression, equals signs, and comment marker are not executed as SQL syntax.
The database is asked to find a username literally equal to the entire payload.

No dummy account has that username, so the query returns no record. The page
stays on the secure login form and displays:

Invalid lab username or password.

The secure result is not caused by trying to remove particular characters. It
is caused by keeping commands and data separate. This is stronger and more
reliable than attempting to block individual SQL keywords or punctuation.

Important limitation:

Using an ORM is safe here because the standard filter API is used. An ORM does
not make every possible operation automatically safe. Developers can still
create SQL injection if they deliberately build raw SQL strings or misuse raw
query features with untrusted input.


8. EXPECTED SECURE-PAGE RESULTS
===============================

Test A - legitimate dummy credentials:

Username: analyst
Password: secengy124!
Expected result: successful lab session.

Test B - same injection attempt:

Username: ' OR 1=1 --
Password: incorrect
Expected result: the page rejects the request with the invalid-credentials
message and does not create a new lab session.


9. SIDE-BY-SIDE COMPARISON
==========================

Vulnerable implementation:

- Builds an SQL command through string interpolation.
- Mixes user-controlled data with SQL syntax.
- Allows the payload to change the WHERE clause.
- Returns a dummy account even though the password is wrong.

Secure implementation:

- Uses Django's standard ORM filter API.
- Sends submitted values as bound data.
- Keeps the SQL structure unchanged.
- Searches for the literal payload as a username and returns no match.


10. SUGGESTED REPORT EVIDENCE
=============================

Keep the evidence concise:

1. Screenshot of the vulnerable form containing the payload and incorrect
   password.
2. Screenshot of the vulnerable result page showing that a lab session opened.
3. Screenshot of the secure form rejecting the identical values.
4. Short vulnerable code extract showing the formatted SQL string.
5. Short secure code extract showing the ORM filter call.
6. A small comparison table containing objective, input, observed result,
   reason, and mitigation.

Suggested lesson statement:

The vulnerable page allowed user input to become executable SQL syntax. The
secure page used the ORM to bind the same input as data, so the payload could
not alter the query's structure. Parameterized queries or correctly used ORM
APIs are the primary defense against SQL injection.
