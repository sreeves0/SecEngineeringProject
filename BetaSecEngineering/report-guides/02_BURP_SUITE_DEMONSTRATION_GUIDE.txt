BETASEC ENGINEERING
BURP SUITE LOCAL DEMONSTRATION GUIDE


1. PURPOSE
==========

This guide explains how to use Burp Suite Community Edition to observe and
manually repeat requests sent to the BetaSec Engineering SQL-injection lab.

The strongest OWASP demonstration available in the current application is:

- OWASP Top 10:2025 A05 - Injection
- OWASP Top 10:2021 A03 - Injection
- CWE-89 - SQL Injection

Burp Suite is the observation and request-manipulation tool. Burp itself does
not create the vulnerability. The vulnerable server-side SQL construction is
what allows the injection.


2. AUTHORIZED SCOPE
===================

Only test this local application:

Host: 127.0.0.1
Port: 8000
Protocol for this stage: HTTP

Allowed paths:

/lab/sql-injection/vulnerable/
/lab/sql-injection/secure/
/lab/sql-injection/result/

Use only the supplied dummy account and classroom payload. Do not scan, probe,
intercept, or attack any third-party site. Do not bind the vulnerable Django
server to 0.0.0.0 or expose it to a LAN or the internet.

Burp Scanner is not required. Burp Suite Community Edition's Proxy, HTTP
history, Inspector, and Repeater are sufficient for this demonstration.


3. PREPARATION
==============

The server is intentionally stopped when this guide was created. Start it only
when you are ready to perform the controlled demonstration.

From the BetaSecEngineering directory, run the local server on the loopback
address:

..\venv-secproject\Scripts\python.exe manage.py runserver 127.0.0.1:8000

If the project is using another valid Python command, the equivalent is:

python manage.py runserver 127.0.0.1:8000

Confirm the application opens at:

http://127.0.0.1:8000/

Dummy lab credentials:

Username: analyst
Password: secengy124!

Classroom payload:

' OR 1=1 --


4. CONFIGURE BURP SAFELY
========================

1. Open Burp Suite Community Edition and create a temporary project.

2. Go to Proxy > Intercept and select Open Browser. Burp's browser is already
   configured to use the local Burp proxy listener.

3. In Burp's browser, open:

   http://127.0.0.1:8000/

4. Add only http://127.0.0.1:8000 to the Burp target scope. In Target > Site
   map or Proxy > HTTP history, select the local host, right-click it, and use
   Add to scope.

5. Configure Proxy history to show in-scope traffic only. This reduces noise
   and helps prevent accidental testing outside the project.

6. Leave Intercept off during ordinary browsing. HTTP history is still
   recorded. Turn Intercept on only when you specifically want to pause and
   inspect one request.

If localhost traffic does not appear, confirm that you are using Burp's own
browser, the default loopback proxy listener is running, and the URL uses
127.0.0.1:8000.


5. DEMONSTRATION A - OBSERVE A NORMAL REQUEST
==============================================

1. In Burp's browser, open the vulnerable page:

   http://127.0.0.1:8000/lab/sql-injection/vulnerable/

2. Sign in using the legitimate dummy credentials:

   Username: analyst
   Password: secengy124!

3. In Burp, open Proxy > HTTP history.

4. Select the POST request to:

   /lab/sql-injection/vulnerable/

5. Inspect the request and identify:

   - The POST method.
   - The application/x-www-form-urlencoded request body.
   - The username parameter.
   - The password parameter.
   - The csrfmiddlewaretoken parameter.
   - The csrftoken cookie.

6. Inspect the response. A successful vulnerable login returns a redirect,
   normally HTTP status 302, with a Location header pointing to:

   /lab/sql-injection/result/

This establishes the normal request format and gives you a controlled baseline
before changing any values.


6. DEMONSTRATION B - REPEAT AND MODIFY THE VULNERABLE REQUEST
==============================================================

1. In Proxy > HTTP history, right-click the captured vulnerable POST request
   and select Send to Repeater.

2. Open the Repeater tab.

3. Keep the existing CSRF form token and cookies. They prove that the request
   came from the local form and prevent an unrelated CSRF failure from hiding
   the SQL-injection result.

4. Use Burp Inspector or the request parameters editor to change only these
   values:

   username = ' OR 1=1 --
   password = incorrect

5. Send the request.

In a raw URL-encoded request body, the username may appear similar to:

username=%27+OR+1%3D1+--

Burp can perform this encoding automatically when you edit the decoded
parameter in Inspector.

6. Inspect the response. The expected vulnerable result is:

   Status: 302
   Location: /lab/sql-injection/result/

This shows that the server opened a lab session even though the password was
incorrect. The vulnerable SQL query allowed the username value to change the
meaning of the WHERE clause.


7. DEMONSTRATION C - SEND THE SAME ATTEMPT TO THE SECURE PAGE
==============================================================

For the clearest comparison, first capture a fresh POST request from the secure
form. This ensures the path, CSRF token, cookie, and form structure are correct.

1. In Burp's browser, open:

   http://127.0.0.1:8000/lab/sql-injection/secure/

2. Submit any values once so a secure POST request appears in HTTP history.

3. Send that secure POST request to a separate Repeater tab.

4. Keep its CSRF token and cookie, then set the same test values:

   username = ' OR 1=1 --
   password = incorrect

5. Send the request.

The expected secure result is:

- HTTP status 200, because the same form is rendered again.
- Response text contains: Invalid lab username or password.
- No redirect to /lab/sql-injection/result/.

The secure view uses Django's ORM. The payload is bound as a literal username
value and cannot alter the SQL command.

9. BURP FEATURES THIS DEMONSTRATES
==================================

Proxy:

- Places Burp between the browser and local web application.
- Records requests and responses in HTTP history.
- Can pause a request before it reaches the server.

HTTP history:

- Shows request methods, paths, parameters, status codes, cookies, and timing.
- Preserves traffic even when Intercept is off.

Inspector:

- Presents form parameters and headers in a structured form.
- Lets you edit a parameter without manually calculating URL encoding.

Repeater:

- Reissues one request multiple times.
- Makes a controlled A/B comparison possible.
- Preserves request and response history for evidence.


10. OWASP TOP 10 COVERAGE
=========================

Directly demonstrated with Burp:

A05:2025 Injection / A03:2021 Injection

The vulnerable and secure Repeater results provide direct evidence of SQL
injection and its prevention.

Separately observable, but better documented in the Wireshark HTTP guide:

A04:2025 Cryptographic Failures / A02:2021 Cryptographic Failures

Burp's HTTP history can show that the connection uses HTTP and has no TLS. The
Wireshark demonstration is stronger evidence because it shows the values on the
wire without relying on an intentionally configured intercepting proxy.

Do not claim that the current project demonstrates the following categories
unless the application is deliberately extended later:

- Broken Access Control
- Security Misconfiguration
- Authentication Failures
- Software Supply Chain Failures
- Insecure Design

Burp can test many categories, but the current application does not contain a
controlled example of each one. A tool's capabilities are not proof that a
particular vulnerability exists.


11. TROUBLESHOOTING
===================

Problem: Burp shows HTTP 403 CSRF verification failed.

Cause: The CSRF cookie or csrfmiddlewaretoken was removed, expired, or copied
from a different browser session.

Fix: Reload the form in Burp's browser, submit it once, and send the new POST
request to Repeater. Keep its CSRF token and cookie unchanged while editing only
the username and password.

Problem: The vulnerable request returns HTTP 200 with an error instead of 302.

Checks:

- Confirm the endpoint is /lab/sql-injection/vulnerable/.
- Confirm the username is exactly: ' OR 1=1 --
- Confirm there is a space between each portion of the payload.
- Confirm the security labs are enabled.
- Confirm the server is running only on 127.0.0.1.

Problem: No localhost requests appear in Burp.

Checks:

- Use Burp's Open Browser button.
- Confirm the proxy listener is running on the loopback interface.
- Use http://127.0.0.1:8000 rather than another host.
- Confirm Proxy history filters are not hiding the request.


12. CLEANUP
===========

1. Turn Intercept off.
2. Close Burp's temporary browser.
3. Stop the Django server.
4. Keep screenshots or saved requests only if they contain dummy project data.
5. Do not export or share cookies from any real site or account.
